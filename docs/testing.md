# 15. Тестовая стратегия

Для проекта предусматриваются три уровня проверки.

## 15.1. Модульные тесты

Модульные тесты должны проверять отдельные правила предметной области.

**Тест 1.** Номер доступен на указанный период.
Ожидаемый результат: резервирование выполняется успешно.

**Тест 2.** Номер уже занят на выбранный период.
Ожидаемый результат: `ROOM_NOT_AVAILABLE`.

**Тест 3.** Дата выселения раньше даты заселения или совпадает с ней.
Ожидаемый результат: `INVALID_BOOKING_PERIOD`.

**Тест 4.** Стоимость проживания рассчитывается исходя
из количества ночей.
Ожидаемый результат: рассчитана корректная итоговая стоимость.

**Тест 5.** Заезд в день выезда предыдущего гостя.
Ожидаемый результат: резервирование выполняется успешно.

## 15.2. Интеграционные тесты

**Сценарий 1. Успешное создание бронирования:**

```
BookingModule → RoomModule → BookingModule
```

Ожидается: номер зарезервирован; бронирование создано.

**Сценарий 2. Номер занят:**

Ожидается: резервирование отклонено; бронирование не создано.

Проверка добавления услуги (`ServiceModule`) будет добавлена после
реализации модуля услуг.

**Сценарий 3. Проверка API** через `WebApplicationFactory`:
коды ответов `201`, `400`, `404`, `409`, `415` для `POST /api/bookings`
и `404` для `GET /api/bookings/{id}`.

## 15.3. Проверка сборки

После внесения изменений должны выполняться:

```bash
dotnet format --verify-no-changes
dotnet build
dotnet test
```

Критерием успешного результата является отсутствие замечаний
`dotnet format`, ошибок сборки и прохождение всех автоматических тестов.

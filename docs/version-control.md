# Правила ведения репозитория

Для проекта используются следующие основные ветки:

- `main`
- `develop`
- `feature/*`
- `fix/*`
- `docs/*`
- `chore/*`

## main

Содержит стабильную версию проекта. Прямые коммиты в `main`
не выполняются, изменения попадают только слиянием из `develop`.

## develop

Используется для объединения результатов разработки.
Создаётся от `main`, все рабочие ветки создаются от `develop`.

## feature/*

Используется для разработки новых функций.

Примеры:

- `feature/booking-creation`
- `feature/room-catalog`
- `feature/guest-services`

## fix/*

Используется для исправления дефектов.

Например:

- `fix/booking-date-validation`

## docs/*

Используется при значительных изменениях документации.

Например:

- `docs/project-artifacts`
- `docs/stage-2-report`

## chore/*

Используется для технических изменений, не затрагивающих
бизнес-логику: настройка репозитория, файлов конфигурации,
структуры решения.

Например:

- `chore/repository-setup`

## Именование веток

- только латинские буквы в нижнем регистре, цифры и дефис;
- после префикса указывается краткое описание задачи;
- одна ветка — одна задача.

# Правила коммитов

Один коммит должен содержать одно логически завершённое изменение.

Используются следующие обозначения:

- `feat:` новая функциональность
- `fix:` исправление
- `docs:` документация
- `test:` тесты
- `refactor:` изменение структуры кода
- `chore:` техническое изменение
- `merge:` слияние веток

Сообщение коммита пишется на русском языке и кратко описывает,
что было сделано.

Примеры:

```
docs: раздел 3 - реестр проектных артефактов
docs: раздел 5 - архитектурная схема
feat: добавлены DTO для бронирования
test: добавлены тесты валидации бронирования
chore: добавлен .gitignore для .NET
```

Не допускаются малоинформативные сообщения:

```
update
fix
work
123
изменения
```

Перед коммитом необходимо проверить состав изменений:

```bash
git status
git diff --staged
```

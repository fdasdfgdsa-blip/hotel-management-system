# Правила ведения репозитория

Для проекта используются следующие основные ветки:

- `main`
- `develop`
- `feature/*`
- `fix/*`
- `docs/*`
- `chore/*`

## main

Содержит стабильную версию проекта. Прямые коммиты в `main`
не выполняются, изменения попадают только слиянием из `develop`.

## develop

Используется для объединения результатов разработки.
Создаётся от `main`, все рабочие ветки создаются от `develop`.

## feature/*

Используется для разработки новых функций.

Примеры:

- `feature/booking-creation`
- `feature/room-catalog`
- `feature/guest-services`

## fix/*

Используется для исправления дефектов.

Например:

- `fix/booking-date-validation`

## docs/*

Используется при значительных изменениях документации.

Например:

- `docs/project-artifacts`
- `docs/stage-2-report`

## chore/*

Используется для технических изменений, не затрагивающих
бизнес-логику: настройка репозитория, файлов конфигурации,
структуры решения.

Например:

- `chore/repository-setup`

## Именование веток

- только латинские буквы в нижнем регистре, цифры и дефис;
- после префикса указывается краткое описание задачи;
- одна ветка — одна задача.

# Правила коммитов

Один коммит должен содержать одно логически завершённое изменение.

Используются следующие обозначения:

- `feat:` новая функциональность
- `fix:` исправление
- `docs:` документация
- `test:` тесты
- `refactor:` изменение структуры кода
- `chore:` техническое изменение
- `merge:` слияние веток

Сообщение коммита пишется на русском языке и кратко описывает,
что было сделано.

Примеры:

```
docs: раздел 3 - реестр проектных артефактов
docs: раздел 5 - архитектурная схема
feat: добавлены DTO для бронирования
test: добавлены тесты валидации бронирования
chore: добавлен .gitignore для .NET
```

Не допускаются малоинформативные сообщения:

```
update
fix
work
123
изменения
```

Перед коммитом необходимо проверить состав изменений:

```bash
git status
git diff --staged
```

# Правила слияния

1. Рабочая ветка создаётся от актуальной `develop`:

   ```bash
   git checkout develop
   git pull
   git checkout -b feature/<название>
   ```

2. Перед слиянием выполняются проверка форматирования, сборка и тесты:

   ```bash
   dotnet format --verify-no-changes
   dotnet build
   dotnet test
   ```

3. Слияние выполняется с созданием merge-коммита (`--no-ff`),
   чтобы в истории было видно, какие коммиты относились к ветке:

   ```bash
   git checkout develop
   git merge --no-ff feature/<название> -m "merge: feature/<название> в develop"
   ```

4. После завершения этапа `develop` сливается в `main` так же
   с `--no-ff`, и на итоговый коммит ставится тег.

5. Слитая рабочая ветка удаляется:

   ```bash
   git branch -d feature/<название>
   ```

## Разрешение конфликтов

При конфликте слияния Git останавливает операцию и помечает
спорные места в файле маркерами `<<<<<<<`, `=======`, `>>>>>>>`.

Порядок действий:

1. Посмотреть список файлов с конфликтом: `git status`.
2. Открыть файл, выбрать правильный вариант или объединить оба,
   удалить маркеры конфликта.
3. Проверить, что маркеров не осталось:

   ```bash
   git diff --check
   ```

4. Добавить файл и завершить слияние:

   ```bash
   git add <файл>
   git commit
   ```

Если слияние нужно отменить: `git merge --abort`.

# Теги

Контрольные состояния проекта отмечаются аннотированными тегами
в формате `vMAJOR.MINOR.PATCH`:

```bash
git tag -a v0.2.0 -m "Этап 2: настройка репозитория"
git push origin v0.2.0
```

| Тег | Состояние |
|-----|-----------|
| `v0.2.0` | Завершён этап 2: репозиторий подготовлен к командной разработке |
| `v0.3.0` | Завершён этап 3: реализованы и интегрированы RoomModule и BookingModule |
| `v0.4.0` | Завершён этап 4: отладка модулей |
| `v0.5.0` | Завершён этап 5: инспекция кода |

# Файлы, которые не хранятся в репозитории

Правила исключения заданы в `.gitignore`. В репозиторий
не попадают:

| Что | Примеры | Причина |
|-----|---------|---------|
| Результаты сборки | `bin/`, `obj/` | Создаются заново командой `dotnet build` |
| Настройки IDE | `.vs/`, `.idea/`, `.vscode/`, `*.user` | Индивидуальны для каждого разработчика |
| Временные файлы и логи | `*.tmp`, `*.log`, `TestResults/` | Не являются исходным кодом |
| Локальная база данных | `*.db`, `*.db-shm`, `*.db-wal` | Создаётся при запуске, у каждого своя |
| Секреты | `.env`, `appsettings.Local.json`, `secrets.json`, `*.pfx`, `*.key`, `*.pem` | Недопустимы в репозитории |

Проверить, каким правилом исключён файл:

```bash
git check-ignore -v <путь>
```

Нормализация переводов строк и признак двоичных файлов
задаются в `.gitattributes`. Единый стиль кода задаётся
в `.editorconfig`.

# Работа с секретами

В репозитории запрещено хранить реальные пароли, токены,
закрытые ключи и строки подключения с паролями.

Для локальной разработки секреты хранятся через
механизм User Secrets:

```bash
dotnet user-secrets init --project src/HotelManagement.Api
dotnet user-secrets set "ConnectionStrings:Default" "<значение>" --project src/HotelManagement.Api
```

Файл секретов хранится в профиле пользователя, вне каталога
репозитория, поэтому не может быть случайно закоммичен.

В `appsettings.json` допускаются только значения без секретов,
например строка подключения к локальному файлу SQLite.

## Если секрет попал в репозиторий

1. Считать секрет скомпрометированным и сразу отозвать
   или заменить его (сменить пароль, перевыпустить токен).
   Удаление файла новым коммитом не помогает: секрет
   остаётся в истории.
2. Удалить файл из отслеживания и добавить его в `.gitignore`:

   ```bash
   git rm --cached <файл>
   ```

3. Если коммит уже опубликован — очистить историю
   (например, `git filter-repo`), выполнить `git push --force`
   и предупредить остальных участников, что им нужно заново
   клонировать репозиторий.

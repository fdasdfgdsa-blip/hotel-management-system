# 2. Назначение и границы проекта

## 2.1. Назначение системы

Разрабатываемая программная система предназначена для автоматизации управления гостиницей: номерным фондом, бронированием, заселением/выселением гостей и дополнительными услугами.

Гость системы должен иметь возможность:

- просматривать доступные номера;
- получать информацию о категориях и стоимости проживания;
- выбирать период проживания;
- оформлять бронирование;
- получать информацию о состоянии бронирования;
- отменять бронирование до заселения;
- заказывать дополнительные услуги.

Администратор гостиницы должен иметь возможность:

- изменять доступность номеров;
- просматривать бронирования;
- выполнять заселение гостя;
- выполнять выселение гостя;
- менять статус номера;
- добавлять дополнительные услуги к бронированию.

---

## 2.2. Основные объекты предметной области

В системе выделены следующие основные сущности:

- гость;
- номер;
- категория номера;
- бронирование;
- период проживания;
- дополнительная услуга;
- статус номера;
- статус бронирования.

Примеры категорий номеров:

- Стандарт (одноместный);
- Стандарт (двухместный);
- Люкс;
- Апартаменты.

---

## 2.3. Границы проекта

### В систему входит

1. Ведение каталога номеров и категорий.
2. Проверка доступности номера на период.
3. Создание бронирования.
4. Расчёт стоимости проживания.
5. Резервирование номера.
6. Изменение статуса бронирования.
7. Заселение и выселение гостя.
8. Учёт дополнительных услуг.
9. Хранение информации о гостях.
10. Просмотр истории бронирований.

### В систему не входит

В рамках курсового проекта не реализуются:

- реальные банковские платежи;
- интеграция с платёжными системами;
- интеграция с внешними OTA (Booking.com, Ostrovok, Суточно.ру);
- система электронных замков;
- мобильное приложение;
- автоматическая отправка SMS/e-mail;
- онлайн-чат с гостем;
- интеграция с системой видеонаблюдения.

Эти функции могут быть добавлены при дальнейшем развитии проекта.

# 4. Перечень модулей системы

В проекте выделено четыре основных функциональных модуля.

| Модуль | Ответственность |
|--------|----------------|
| RoomModule | Хранение информации о номерах и проверка их доступности |
| BookingModule | Создание и управление бронированиями |
| ServiceModule | Создание и управление дополнительными услугами |
| GuestModule | Хранение информации о гостях |

Дополнительно используется `ApiHost`, который принимает запросы
от пользовательского интерфейса и передаёт их соответствующим модулям.

## 4.1. RoomModule

Отвечает за номерной фонд гостиницы.

Основные функции:

- получение списка номеров;
- получение информации о номере;
- проверка доступности на выбранный период;
- резервирование номера;
- снятие резерва;
- изменение состояния номера.

Пример состояний:

- Available
- Reserved
- Occupied
- Cleaning
- Maintenance

## 4.2. BookingModule

Отвечает за бронирование номеров.

Основные функции:

- создание бронирования;
- расчёт стоимости проживания;
- изменение периода проживания;
- подтверждение бронирования;
- отмена бронирования;
- заселение и выселение гостя.

Модуль взаимодействует с:

- RoomModule
- ServiceModule
- GuestModule

## 4.3. ServiceModule

Отвечает за дополнительные услуги гостиницы.

Основные функции:

- ведение каталога услуг;
- добавление услуги к бронированию;
- расчёт стоимости услуг;
- удаление услуги из бронирования;
- изменение статуса услуги.

Пример состояний:

- Added
- Provided
- Cancelled

## 4.4. GuestModule

Отвечает за работу с гостями.

Основные функции:

- регистрация гостя;
- получение данных гостя;
- изменение контактных данных;
- просмотр истории бронирований.

## Описание схемы

| Компонент | Назначение |
|-----------|-----------|
| ApiHost | Точка входа: приём и маршрутизация HTTP-запросов |
| BookingModule | Создание и управление бронированиями |
| RoomModule | Номерной фонд и проверка доступности номеров |
| GuestModule | Хранение и управление данными гостей |
| ServiceModule | Учёт дополнительных услуг гостиницы |
| SQLite / EF Core | Хранение данных в учебной версии проекта |

Центральным модулем бизнес-процесса является `BookingModule`.

При создании бронирования он:

1. получает данные гостя из `GuestModule`;
2. проверяет доступность номера в `RoomModule`;
3. резервирует номер в `RoomModule`;
4. создаёт бронирование;
5. при необходимости добавляет услуги через `ServiceModule`.

Бизнес-модули не обращаются к внутренним классам друг друга напрямую:
взаимодействие выполняется только через публичные интерфейсы и DTO
из слоя Contracts, например:

```
BookingModule ──► IRoomReservationService ──► RoomModule
```

Это обеспечивает слабую связанность и тестируемость модулей.

# 11. Протокол взаимодействия № 1
## Резервирование номера

## 11.1. Инициатор и получатель

Инициатор: `BookingModule`
Получатель: `RoomModule`

## 11.2. Назначение

Протокол используется при создании бронирования.
Перед сохранением бронирования необходимо убедиться, что выбранный
номер свободен на необходимый период, и зарезервировать его.

## 11.3. Механизм вызова

Асинхронный вызов через интерфейс C#: `IRoomReservationService`.
Зависимость передаётся через механизм Dependency Injection.

## 11.4. Точка входа

```csharp
Task<ReserveRoomResult> ReserveAsync(
    ReserveRoomRequest request,
    CancellationToken cancellationToken);
```

## 11.5. Формат запроса

```json
{
  "roomId": "a1b2c3d4-1234-5678-abcd-ef1234567890",
  "bookingId": "f9e8d7c6-4321-8765-dcba-fe0987654321",
  "checkInDate": "2026-10-01",
  "checkOutDate": "2026-10-05"
}
```

## 11.6. Успешный ответ

```json
{
  "success": true,
  "errorCode": null
}
```

## 11.7. Ошибки

Возможные ошибки:

| Код | Описание |
|-----|----------|
| ROOM_NOT_FOUND | Номер не существует |
| ROOM_NOT_AVAILABLE | Номер занят на выбранный период |
| INVALID_BOOKING_PERIOD | Некорректный период проживания |

Пример:

```json
{
  "success": false,
  "errorCode": "ROOM_NOT_AVAILABLE"
}
```

## 11.8. Таймаут

Операция должна завершиться не более чем за 3 секунды.
При отмене запроса используется `CancellationToken`.

## 11.9. Повторная отправка

Автоматический повтор операции резервирования не выполняется.
Причина: повторный вызов без дополнительной проверки может привести
к неоднозначному состоянию резерва.
Повтор операции выполняется только после проверки результата
предыдущего вызова.

## 11.10. Аутентификация

Дополнительная аутентификация между модулями не выполняется,
поскольку они работают внутри одного серверного приложения.
Проверка прав пользователя выполняется на уровне API.

## 11.11. Версия контракта

`RoomReservationContract v1`

## 11.12. Пример обмена

```
BookingModule
       │
       │ ReserveAsync(...)
       ▼
 RoomModule
       │
       │ Проверка номера
       │ Проверка периода
       │ Создание резерва
       ▼
 ReserveRoomResult
       │
       ▼
 BookingModule
```

При успешном резервировании `BookingModule` продолжает создание
бронирования. При ошибке `ROOM_NOT_AVAILABLE` бронирование не создаётся.

# 12. Протокол взаимодействия № 2
## Добавление услуги к бронированию

## 12.1. Инициатор и получатель

Инициатор: `BookingModule`
Получатель: `ServiceModule`

## 12.2. Назначение

После успешного создания бронирования необходимо зарегистрировать
дополнительную услугу, привязанную к бронированию.

## 12.3. Механизм вызова

Асинхронный вызов через интерфейс: `IBookingServiceService`.

## 12.4. Точка входа

```csharp
Task<ServiceDto> AddAsync(
    AddServiceRequest request,
    CancellationToken cancellationToken);
```

## 12.5. Формат запроса

```json
{
  "bookingId": "f9e8d7c6-4321-8765-dcba-fe0987654321",
  "serviceId": "b2c3d4e5-5678-abcd-1234-ef5678901234",
  "quantity": 2,
  "serviceDate": "2026-10-02T08:00:00"
}
```

## 12.6. Успешный ответ

```json
{
  "id": "c3d4e5f6-9012-cdef-5678-0123456789ab",
  "bookingId": "f9e8d7c6-4321-8765-dcba-fe0987654321",
  "serviceId": "b2c3d4e5-5678-abcd-1234-ef5678901234",
  "name": "Завтрак",
  "price": 500.00,
  "quantity": 2,
  "status": "Added"
}
```

## 12.7. Ошибки

| Код | Описание |
|-----|----------|
| BOOKING_NOT_FOUND | Бронирование не найдено |
| SERVICE_NOT_FOUND | Услуга не существует |
| INVALID_QUANTITY | Некорректное количество |
| SERVICE_ALREADY_ADDED | Услуга уже добавлена к бронированию |

Пример ошибки:

```json
{
  "success": false,
  "errorCode": "SERVICE_NOT_FOUND"
}
```

## 12.8. Таймаут

Максимальное ожидаемое время выполнения: 3 секунды.

## 12.9. Повторная отправка

Повторный запрос допускается только после проверки того, что услуга
для данного бронирования ещё не добавлена.
`BookingId` + `ServiceId` используется для предотвращения создания
дублирующих записей.

## 12.10. Аутентификация

Внутренняя аутентификация между модулями не требуется.
Доступ к операции добавления услуги предварительно проверяется
на уровне API.

## 12.11. Версия контракта

`ServiceBookingContract v1`

## 12.12. Пример обмена

```
BookingModule
      │
      │ AddAsync(...)
      ▼
ServiceModule
      │
      │ Проверка бронирования
      │ Проверка услуги
      │ Добавление записи
      ▼
ServiceDto
      │
      ▼
BookingModule
```

# 13. Общий сценарий создания бронирования

После определения двух протоколов полный процесс создания

```
Гость
   │
   │ Создаёт бронирование
   ▼
 ApiHost
   │
   ▼
 BookingModule
   │
   ├──────────────► GuestModule
   │                 Проверка гостя
   │
   ├──────────────► RoomModule
   │                 Проверка и резервирование
   │                 номера
   │
   │ Создание Booking
   │
   └──────────────► ServiceModule
                     Добавление услуги
```

Результатом операции является созданное бронирование
с зарезервированным номером и зарегистрированными
дополнительными услугами.

# 15. Тестовая стратегия

Для проекта предусматриваются три уровня проверки.

## 15.1. Модульные тесты

Модульные тесты должны проверять отдельные правила предметной области.

**Тест 1.** Номер доступен на указанный период.
Ожидаемый результат: резервирование выполняется успешно.

**Тест 2.** Номер уже занят на выбранный период.
Ожидаемый результат: `ROOM_NOT_AVAILABLE`.

**Тест 3.** Дата выселения раньше даты заселения.
Ожидаемый результат: `INVALID_BOOKING_PERIOD`.

**Тест 4.** Стоимость проживания рассчитывается исходя
из количества ночей.
Ожидаемый результат: рассчитана корректная итоговая стоимость.

## 15.2. Интеграционные тесты

**Сценарий 1. Успешное создание бронирования:**

```
BookingModule → RoomModule → BookingModule → ServiceModule
```

Ожидается: номер зарезервирован; бронирование создано; услуга добавлена.

**Сценарий 2. Номер занят:**

Ожидается: резервирование отклонено; бронирование не создано;
услуга не добавлена.

## 15.3. Проверка сборки

После внесения изменений должны выполняться:

```bash
dotnet build
dotnet test
```

Критерием успешного результата является отсутствие ошибок сборки
и прохождение всех автоматических тестов.

# 18. Журнал технических решений

Для значимых решений проекта используется каталог `docs/decisions/`.
В рамках данного этапа решения зафиксированы в этом отчёте.

## ADR-001. Использование модульной архитектуры

**Статус:** Принято.

**Проблема:** Необходимо разделить функции системы таким образом,
чтобы изменение работы бронирования не приводило к изменению
каталога номеров или логики гостей.

**Решение:** Разделить приложение на функциональные модули:
Rooms, Booking, Services, Guests.

**Причина:** Такое разделение позволяет:

- определить ответственность компонентов;
- уменьшить связанность;
- независимо тестировать бизнес-логику;
- упростить последующее расширение проекта.

## ADR-002. Взаимодействие через контракты

**Статус:** Принято.

**Проблема:** Прямое обращение одного модуля к внутренним классам
другого увеличивает связанность приложения.

**Решение:** Взаимодействие модулей выполнять через публичные
интерфейсы и DTO.

Например:

```
BookingModule
        ↓
IRoomReservationService
        ↓
RoomModule
```

**Последствия.**

Положительные:

- модули слабее связаны;
- проще выполнять тестирование;
- контракт взаимодействия можно изменить контролируемо.

Отрицательные:

- необходимо поддерживать дополнительные DTO и интерфейсы.

# 23. Оставшиеся риски

На данном этапе выявлены следующие риски.

**Риск 1. Одновременное резервирование.**
Два гостя могут попытаться забронировать один номер на одинаковый
период. На этапе реализации необходимо обеспечить защиту
от одновременного резервирования.

**Риск 2. Ошибка после резервирования.**
Номер может быть успешно зарезервирован, но создание бронирования
завершится ошибкой. Необходимо предусмотреть отмену резерва.

**Риск 3. Ошибка добавления услуги.**
Бронирование может быть создано, но услуга не зарегистрирована.
Необходимо определить способ повторной обработки операции.

**Риск 4. Изменение контрактов.**
При изменении DTO необходимо контролировать совместимость
взаимодействующих модулей.
